# Rename CNPG clusters by promoting a replica, upgrade them in place, never both at once

**Status:** accepted
**Date:** 2026-09-03

Two clusters needed a rename and a PostgreSQL major upgrade: `pgsql-cluster` → `pgcluster-default` and `pgvector-cluster` → `pgcluster-vector`, both 17 → 18. A CNPG `Cluster` cannot be renamed — `metadata.name` fixes the PVC names, the `-rw`/`-ro`/`-r` Services and, through the `&name` anchor, the barman prefix — so a rename is structurally a blue/green cutover. The upgrade is the opposite shape: CNPG's declarative in-place major upgrade keeps the name and the PVCs and swaps the data directory underneath.

Each cluster therefore moved twice, with a soak between. The rename was a **promoted physical replica**: the new-name cluster ran with `replica.enabled: true` against blue's object store, followed production for days, and was promoted in a cutover that began with `pg_switch_wal()` on a quiesced blue. The upgrade was a separate commit that changed `imageName` only.

The `pgvector` pair carried a third variable — `vchord` 0.4.2 → 1.1.1 — and it got its own move as well, on PostgreSQL 17, ahead of the version jump.

## Considered options

**Rename and upgrade in one cutover.** Rejected on mechanism: a physical replica cannot cross a major version, so the new cluster must start on the old one, and `pg_upgrade` runs with `--link` and replaces the original PGDATA on success. Combining them means the moment the upgrade succeeds there is no intact PG17 copy under the new name to fall back to. Separating them keeps a free abort on each half.

**Rename by restoring from a backup**, which is how [#1211](https://github.com/tscibilia/home-ops/issues/1211) did `postgres16` → `pgsql-cluster`. Rejected after reading it: that migration created and verified the new cluster while the apps were still writing (§1.5–1.6) and stopped them afterwards (§1.8), so every write between the recovery point and the quiesce was silently lost. A replica that keeps replaying archived WAL closes that window; `pg_switch_wal()` after quiescing closes the remainder, because `archive_timeout` is 300s and the last partial segment would otherwise stay on blue.

**Logical migration via `bootstrap.initdb.import`.** Attractive because it could have dropped the orphan databases at copy time. Rejected because the import is one-shot — a second pass to catch up requires deleting the cluster and its PVCs — so the real import would have had to run with the apps already down, turning a 5-minute cutover into however long `pg_dump`/`pg_restore` takes.

**Streaming replication instead of archive-following.** Rejected as more moving parts for no gain: it needs new credentials and a network path between clusters, where the object store was already there and already trusted.

## Consequences

- **The rename cutover is a promotion plus a `CNPG_NAME` repoint, not a restore.** Both ran in under a minute of database work: the replica reached the switch LSN in 8 seconds (vector) and 1 second (default). Promotion is irreversible — disabling `replica` makes the cluster a standalone primary — so the rollback is "point `CNPG_NAME` back at blue", which is why blue is kept until after the soak rather than deleted with the cutover.
- **`serverName` must change at each upgrade, `barmanObjectName` must not.** `pg_upgrade` resets the timeline to 1 and assigns a new system ID, so the PG18 WAL stream is not continuous with the PG17 one. They live under `pgcluster-default-v18` and `pgcluster-vector-v18`; sharing a prefix would make a restore ambiguous. `barmanObjectName` keeps the `&name` anchor, so the two are no longer the same value and the anchor cannot be reused for both.
- **`PG_VER` moves in the same commit as the cluster it serves.** `pg_dump` 17 cannot dump from a PG18 server, so a lagging `PG_VER` breaks that app's nightly dump to clonenas silently — the CronJob fails, nothing else notices. The component default carries nine apps; the rest pin it explicitly.
- **A survey that greps `CNPG_NAME` misses consumers.** Five did not use it: `cetranscript` and `gatus` embedded the host in their connection URL, `pgadmin` names clusters in `servers.json`, and `immich` and `memini` also carried `dependsOn` on the old Kustomization. Because blue keeps running until it is deleted, missing one does not error — the app connects to the old cluster and keeps writing there. Grep the literal cluster name across `kubernetes/apps`, `kubernetes/components` and `docs/context`, and confirm membership from `pg_stat_activity` rather than from labels.
- **Extension upgrades and PostgreSQL upgrades break different things.** `ALTER EXTENSION vchord UPDATE` took 0.4.2 to 1.1.1 in one step, reported success, and left all four `vchordrq` indexes reporting `indisvalid=true` — while every vector query failed with `deserialization: bad version number`. The on-disk index format changed and PostgreSQL cannot see it. `pg_upgrade` afterwards needed no second rebuild. So the REINDEX is owed to the extension jump, and `indisvalid` is not a usable check for it; only running a query is.
- **Verify the way the app queries, not the way the cluster reports.** Every SQL check passed while immich's text search was broken, because the SQL compared a stored embedding and never exercised the text-to-embedding path — an unrelated `immich-ml` fault, found by a human. A "search works" check must also match how that index was built: `clip_index` is `vector_cosine_ops` with `lists=[1]`, `idx_memories_vec` is `vector_l2_ops` with none, and using the wrong operator makes the planner seq-scan and still return rows.
- **A rehearsal on an idle clone under-reports.** `pg_upgrade` took 45s on a clone and 90s on the live cluster with the same data. Budget a rehearsal figure at roughly 2x. The upgrade Job is also named after the **current primary**, not instance 1 — after a promotion that is rarely `-1`.
- **The merge is inside the outage, so the PR must exist before it starts.** The first cutover spent ~11 of its ~14 minutes with the apps down, waiting on a commit to be signed, pushed, PR'd and merged; the database had been ready for 8 seconds. Push the branch and open the PR before quiescing — and say explicitly that the merge waits for a go, or the instruction reads as permission to merge immediately.
- **Neither old cluster is deleted with its cutover.** `pgsql-cluster` and `pgvector-cluster` stay as warm PG17 copies through both the rehearsal and the real upgrade, at a cost of 704 MB and 254 MB against 56 GB free. Deleting them removes the `ObjectStore` resource, not the B2 objects, which age out under the 7-day retention.
